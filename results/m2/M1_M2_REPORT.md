## 1. What the review asked

- M1: the published comparison (direct-mapped wins on 12/12 kernels) compares two different controllers. The DM
  point uses a five-state controller; SA2 and DM_VC4 use a ten-state DSE core whose main-array hit costs one
  extra cycle (ST_LOOKUP -> ST_HIT_RESP / ST_CPU_RESP). Controller cost must be separated from organisation.
- M2: one capacity and one line size is not a design space. Sweep capacity, line size, associativity and victim
  depth.

## 2. Method

- RTL: R15 (manifest d409b09d) for the base sweep; R16 (manifest c09143ea; hdl identical to ea3ef852) adds a
  parameter FAST_HIT to the DSE and N-way cores. With FAST_HIT = 1 a main-array hit is answered in ST_LOOKUP,
  so the DSE core's hit latency equals the DM controller's. FAST_HIT = 0 (default) is proved equivalent to R15
  (section 6).
- Organisations: DM (CACHE_CONFIG 0, five-state controller), DM_DSE (3: the DSE core used as a plain
  direct-mapped cache), SA2 (1), DM_VC4 (2, victim buffer), SA4 (4, N-way core, PLRU). Capacity = sets x ways x
  line bytes, identical for every organisation at a point.
- Grid (`scripts/m2/run_m2_sweep.py`): A = capacity 256 B .. 8 KiB x {DM, DM_DSE, SA2, VC4, SA4}, 16 B lines;
  B = 1 and 4 KiB x lines 8 / 32 B x {DM_DSE, SA2, VC4, SA4} (the DM controller supports 16 B lines only);
  C = 1 and 4 KiB x victim depth 2 / 8. 50 points x 13 workloads = 650 runs (R15); 44 points x 13 = 572 runs
  with FAST_HIT (DM has no FAST variant). SA4 at 256 B does not elaborate (4 sets < the L0's 3 index bits).
- Workloads: the 12 upstream Embench-IoT kernels (fw/up_*.hex) and CoreMark, BP on, L0 8 entries, RAM 16 KiB.
  Every run passes the harness self-check and the counter invariants (exclusive hit/miss accounting).
- Every measurement twice (independent executions, separate log trees), compared field by field.
- Cross-check: the 4 KiB / 16 B rows of the sweep reproduce the frozen R15 chain results (65 rows, every field).

result. Below 1 KiB set associativity wins even on the slower controller.

+0.11 %, +0.01 % (4 KiB), 0.00 % (8 KiB); cycle-identical on 5, 6, 9, 9, 12 and 13 of 13 workloads. The residual
is in the D-cache only (the two D$ controllers differ in the L0 and in store-miss handling: d_main / d_miss differ,
every I$ counter is equal), e.g. up_matmult-int at 4 KiB: 6 more D$ misses, +0.096 %.

"X beats Y".

## 4. Why DM_VC4 loses although it misses less

VC4 has the lowest miss rates of all organisations (e.g. 256 B: I$ 4.02 % vs 4.66 %, D$ 26.8 % vs 34.2 %, AXI
read beats -26 %) yet is the slowest. The cores copy the evicted line into the victim buffer BEFORE the refill
starts, one word per state (I$: ST_EVICT_READ + 4 x ST_EVICT_WRITE, about 5 cycles; D$: READ/WRITE per word,
about 8 cycles), on every miss to a valid line, and a victim hit pays a swap of the same length. Measured at 256 B
(FAST data, sums over 12 kernels): the I$ converts 8,632 misses into victim hits but its stall cycles grow by
278,890; the D$ converts 20,919 misses and its stall cycles are flat (+2,080). The I$ sees few victim hits per
miss, the D$ many. up_nettle-sha256 at 4 KiB has zero victim hits and the same 3,414 I$ misses as DM, and runs
+17.9 % slower: that is the eviction cost alone. This is a property of this micro-architecture (eviction
serialised with the refill instead of overlapping the AXI latency), not of victim caches in general.

32 B lines are better than the published 16 B at 4 KiB for every organisation (-4.7 to -5.4 % with the matched
controller); 8 B lines are clearly worse. The controller confound also distorts line-size conclusions: with the
extra hit cycle the 8 B penalty looks almost twice as large (+19-22 % instead of +12-13 %), because shorter lines
make the 8-entry L0 cover fewer bytes, so more accesses pay the main-array hit.

Victim depth (FAST, vs VC4): VC2 +2.58 % (1 KiB) / +0.23 % (4 KiB); VC8 -1.34 % / -0.45 %; CoreMark within
+/-0.33 %. Depth matters little next to the eviction cost of section 4.

  SA2 +456 LE, Fmax Slow-85C 53.71 -> 51.65 MHz (-3.8 %), +5.4 mW; DM_VC4 +115 LE, 54.90 -> 55.35 MHz, +3.6 mW;

  and the LE increases are likely real. At the fixed 50 MHz clock the cycle gains of section 3 are kept in full;
  at each point's own Fmax, SA2's -9.0 % cycles at 4 KiB shrink to about -5.3 % time (0.9103 x 53.71 / 51.65 = 0.9466). The FAST_HIT 0 points are
  identical to the R14 / R15 fits on all 115 recorded fields (runtime excepted). No ASIC build of a FAST point.
- The residual DM vs DM_DSE_fast difference (D$ L0 / store-miss policy) is not removed; it is <= 1.1 % and
  vanishes at 4-8 KiB.
- VC4's eviction is serialised with the refill; overlapping it with the AXI latency is the obvious fix and is not
  implemented.
- Single-issue in-order core, one memory system, 13 workloads; simulation only (no board available).
